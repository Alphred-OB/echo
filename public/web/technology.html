Acoustic Channel

A one-time code, carried on sound you can't hear

Echo transmits single-use session nonces over high-frequency audio, decoded on the phone with no native app — just a browser and a microphone.

ggwave WASM encoding

The payload is modulated using ggwave, an open-source data-over-sound library compiled to WebAssembly and run entirely client-side. Each frame carries the nonce with built-in error correction, so brief dropouts from background noise don't corrupt the code.

Why 15–19.5 kHz

This band sits at the overlap of two hard constraints: it's above where most adult hearing meaningfully picks up tones, and it's still within the frequency response of ordinary phone and laptop microphones.

Push much past ~20 kHz and reliability drops — consumer transducers and standard 44.1/48 kHz sample rates weren't built for true ultrasound, so this band is close to the practical ceiling, not an arbitrary choice.

Device-Bound Cryptography

Sound carries the nonce. A signature proves identity.

The acoustic channel is low-bandwidth and unauthenticated by itself — the actual proof of identity is a public-key signature, computed on-device with a key that never leaves it.

Key generation & storage

During enrollment, the phone generates a P-256 elliptic-curve key pair with the WebCrypto API, marked extractable: false. The private key is created and used entirely inside the browser's secure key storage — Echo's own code never has a way to read it out, export it, or transmit it.

crypto.subtle.generateKey(
  { name: "ECDSA", namedCurve: "P-256" },
  false, ["sign", "verify"]
)
extractable = false — non-exportable by construction

Signature payload

The phone signs a domain-prefixed message over the nonce it heard, using ECDSA with SHA-256. The prefix binds a signature to Echo's own protocol version so it can never be mistaken for a signature meant for something else.

"echo-v1|<nonce>"
Algorithm: ECDSA / SHA-256 · Curve: NIST P-256

Phishing note: the signature proves possession of the enrolled key, not which site requested it — see the Security FAQ for how domain-relay phishing is mitigated.

Protocol Parameters

Session lifecycle, in numbers

Every token in the sign-in flow is single-use and time-boxed server-side. These are the actual values enforced by the backend.

TokenSizeLifetimeNotes
Login nonce 96-bit 30 seconds Burned atomically on verification; a new request instantly invalidates any prior one.
Session cookie 256-bit 8 hours HttpOnly, SameSite=Strict, Secure in production.
Enroll token 128-bit 10 minutes Single-use QR/link for attaching a new device key to an account.
Magic-link token 256-bit 15 minutes Email fallback for when the phone is unavailable; single-use.
